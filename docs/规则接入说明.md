# Surge 与 Loon 规则接入说明

仓库按客户端分别保存规则：`Surge/` 和 `Loon/`。同名 `.list` 文件应保持内容一致。规则文件只负责匹配域名或 IP；每条规则集在主配置中绑定的策略，决定实际使用的代理策略。

## 推荐顺序

把具体服务规则放在 Google 通用规则之前，特别是 `Google.list` 中的 `DOMAIN-KEYWORD,google` 会匹配大量 Google 相关域名，可能覆盖 Gemini 和 YouTube 的 Google API 请求。

推荐按以下顺序引用：

1. YouTube
2. Gemini
3. Copilot
4. ChatGPT
5. Claude
6. Telegram
7. Apple
8. Netflix / Disney+
9. Google（最后）

如果 YouTube、Gemini、Copilot 需要不同策略，应确保它们在 Google 通用规则之前。若这些服务走同一策略，顺序依然建议保留，便于以后分别调整。

## Surge 规则段

将下面的 `Proxy` 替换成 Surge `[Proxy]` 或 `[Proxy Group]` 中已有的策略名。示例按本仓库的本地规则文件路径编写；将规则段合并进主配置的 `[Rule]`，并保证规则集排列顺序不被其他规则打乱。

```ini
[Rule]
RULE-SET,./Surge/YouTube.list,Proxy
RULE-SET,./Surge/Gemini.list,Proxy
RULE-SET,./Surge/Copilot.list,Proxy
RULE-SET,./Surge/ChatGPT.list,Proxy
RULE-SET,./Surge/Claude.list,Proxy
RULE-SET,./Surge/Telegram.list,Proxy
RULE-SET,./Surge/Apple.list,Proxy
RULE-SET,./Surge/Netflix_Disney+.list,Proxy
RULE-SET,./Surge/Google.list,Proxy
FINAL,Proxy
```

如果规则文件没有放在配置文件的相对路径下，可将 `./Surge/...` 改为 Surge 可访问的本地路径，或改用已发布的 HTTPS 规则链接。`FINAL,Proxy` 是示例兜底策略，可按自己的分流需求改为 `DIRECT` 或其他策略。

## Loon 规则段

Loon 的规则订阅格式是“规则文件 URL,策略名”。将 `Proxy` 换成 Loon 中已有的策略名。下面使用此仓库 `main` 分支的 raw 链接；只有规则文件已提交并推送到 GitHub 后，链接才能访问。

```ini
[Rule]
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/YouTube.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Gemini.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Copilot.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/ChatGPT.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Claude.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Telegram.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Apple.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Netflix_Disney+.list,Proxy
https://raw.githubusercontent.com/ilovn/Air-Rules/main/Loon/Google.list,Proxy
FINAL,Proxy
```

Loon 会优先应用本地规则，其次是插件规则，最后是订阅规则。因此，如果主配置或插件里已经有覆盖范围很广的本地规则，仅调整这里的订阅顺序不一定能改变最终命中结果；需要检查并调整那条本地规则。

## 生效前检查

- `Proxy` 必须是客户端中已存在的策略名称；否则将其换成实际名称。
- `FINAL` 是未命中规则时的兜底策略。根据自己的默认网络行为选择 `Proxy` 或 `DIRECT`。
- Surge 本地规则集路径需按配置文件实际位置确认。Loon 的远程订阅需要规则文件已发布到可访问的 URL。
- 更新 Surge 和 Loon 中的规则后，可在请求记录中查看命中的规则和策略，确认规则顺序与预期一致。
- 通用 Google 规则保持最后；如未来增加其他范围较大的关键词规则，也应检查它们与具体服务规则的先后关系。
- Gemini、YouTube、Google 三组规则建议绑定到同一个稳定的代理策略/出口。即使域名匹配正确，不同出口或地区也可能让同一会话中的 Google 请求表现为不同来源，并触发 403。
- Loon 的本地规则优先级高于插件和规则订阅。若本地 `[Rule]` 仍有 `DOMAIN-SUFFIX,google.com`、`DOMAIN-SUFFIX,googleapis.com` 或 `DOMAIN-KEYWORD,google`，它们会先于这里的 Gemini/YouTube 订阅规则命中；应删除重复的本地宽泛规则，或把相关规则统一放在同一来源并按服务规则优先排列。
- 出现 403 时先检查请求记录里的实际命中规则、策略和节点；若三组规则已走同一固定出口仍报错，再检查 Google 返回的错误类型、账号地区及该出口是否被服务端限制。

## 本次检查结论与覆盖边界

- 已移除 Gemini 规则中的通用 `google.com`、`googleapis.com` 和 Google 基础服务条目，避免 Gemini 策略接管全部 Google 流量。
- 已移除 YouTube 规则中的通用 `google.com`，并把 YouTube API 主机 `youtubei.googleapis.com` 放入专属规则，避免被末尾的 Google 关键词规则抢先匹配。
- Google 通用规则仍保留 `DOMAIN-KEYWORD,google` 以扩大基础服务覆盖；它会匹配很多 Google 相关主机，因此必须置于具体服务规则之后。
- ChatGPT、Microsoft Copilot、Apple 和 Telegram 列表已补充官方网络文档列出的客户端依赖或入口域名。服务端点会更新，规则集不能保证覆盖每个地区、设备和新功能。
- Telegram 的 IPv4 网段是静态规则，服务端地址可能变化；ChatGPT 语音还可能使用动态 IP 的 UDP 3478，单靠这些域名规则无法完整覆盖。
- Netflix/Disney+ 的播放依赖 CDN、地区和设备。若某设备仍无法播放，应根据客户端请求日志补充实际缺失的主机，而不是无限扩大到通用 CDN 域名。

本次域名核对参考了 [OpenAI 网络建议](https://help.openai.com/en/articles/9247338-network-recommendations-for-chatgpt-errors-on-web-and-apps)、[Microsoft Copilot 网络要求](https://learn.microsoft.com/en-us/microsoft-365/copilot/microsoft-copilot-requirements)、[Apple 企业网络主机列表](https://support.apple.com/en-ca/101555)、[Telegram FAQ](https://www.telegram.org/faq) 和 [Netflix 网络故障说明](https://help.netflix.com/en/node/100242)。
